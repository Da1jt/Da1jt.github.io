ISCC practice / Local label A22

When a stack canary becomes readable

The problem

This challenge accepts input, echoes data, and accepts another input. My archived write-up identifies an overflow in this sequence. The supplied binary uses a stack canary, a value checked before a function returns, and has a fixed executable layout rather than position-independent code.

My analysis

I followed the two input stages separately. The first input and echo can disclose the canary. Knowing that value changes the second stage: the recorded approach preserves it while changing the saved control-flow data. The binary already provides a useful function and string, so the analysis does not depend on first discovering the address of a shared library.

What the note demonstrates

The write-up connects an information disclosure to a later memory-corruption step. It shows why listing enabled protections is only the start of an analysis: their effectiveness depends on what the application exposes. This is a summary of the archived solution approach, not a newly measured success rate.

Defensive takeaway

Bound input at every entry point and check what an echo can reveal. A stack canary can detect many overwrites, but it does not repair an information leak or make an unbounded input safe.

ISCC practice / Local label A23

A freed object that remains accessible

The problem

This menu-driven challenge supports allocation, deletion, editing, and display. My notes identify a use-after-free: a deleted slot can still be displayed or edited. The stale read and stale write have different consequences, even though both come from the same object-lifetime mistake.

My analysis

The recorded solution first examines a freed allocation larger than the small-allocation cache to obtain information about the runtime library. It then uses a stale write on smaller cached allocations to influence where a later allocation lands. The write-up pays attention to the cache’s entry count as well as its linked-list state; changing a pointer alone is not enough to explain the allocation sequence.

What the note demonstrates

The analysis links three layers: the application’s slot table, the allocator’s bookkeeping, and a control-flow target in the supplied runtime. The archived script relies on a hook available in that challenge’s library version. That detail is specific to the supplied environment and should not be generalized to current allocators.

Defensive takeaway

Invalidate a slot when its object is freed, reject subsequent reads and writes through it, and make ownership explicit. Preventing stale access addresses the cause before allocator protections become relevant.

picoCTF practice / SilentStream

Reconstructing an image from a byte stream

The problem

The challenge materials include a packet capture, exported packet data, and a small encoder. The encoder shifts each byte by a constant and wraps the result at 256. Recovering the original file requires both reversing that transformation and retaining the order of the transmitted data.

My analysis

I inspected the encoder, extracted the payload fields from the packet export, and concatenated them in packet order. I reversed the byte transformation and checked the recovered file signature. The result begins with a JPEG/JFIF header, providing a concrete check that the output is image data rather than arbitrary decoded bytes.

Recorded result

The local archive contains the reconstructed byte stream and a saved JPEG, and the write-up records recovering the challenge text from the image. An offline check of the supplied packet export reproduced the saved decoded byte stream exactly. This establishes the reconstruction described here; it does not establish a competition score or ranking.

What I learned

A useful reverse-engineering workflow combines a simple model of the transformation with an independent format check. Packet order and file signatures can be as important as understanding the encoding operation itself.
